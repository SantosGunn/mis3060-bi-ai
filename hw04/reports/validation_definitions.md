# Validation definitions (Part D)

Generated by `scripts/03_validate.py`. Both stages (raw, clean) are evaluated in one run with the same original columns and the same rule definitions. Cleaning flag columns are excluded from every metric. All figures are computed from the data.

## Referential integrity: `check_referential_integrity(fact_df, fact_key, dim_df, dim_key)`

- Exact text matching: `45.0` does not match `45`. Keys are compared with `isin`, so rows never multiply.
- Blank (empty or whitespace-only) child keys are excluded from the match rate and reported as `null_key_rate_pct = blank child keys / child rows`.
- `match_rate_pct = matched nonblank child keys / nonblank child keys`. Blank parent keys never match.
- `orphan_rows = nonblank child keys - matched`; `distinct_orphan_keys` counts different orphan values.
- Any rate whose denominator is 0 (empty table, all-blank keys) is N/A, not 0% or 100%.
- Parent-key uniqueness is checked separately (`validation_parent_keys.csv`).
- 13 relationships: 10 ID-based and 3 to `dim_date.date`; 26 evaluations (2 stages).

## Scorecard metrics (`data_quality_scorecard.csv`, one row per table per stage)

| Metric | Numerator | Denominator |
|---|---|---|
| % completeness | applicable cells that are nonblank | applicable cells (original columns); structurally not-applicable cells are excluded (sector for non-equity, expense_ratio_bps for non-ETFs, security_id/shares/price on Deposit, Withdrawal, Advisory Fee rows). Blank risk_profile counts as incomplete. The text `None` in certifications is a valid value, so it counts as complete. |
| % key uniqueness | rows whose primary key is nonblank and appears exactly once | rows |
| % type validity | applicable nonblank cells that match the expected format (strict integer text for integer columns, so `45.0` fails) and, for numeric columns, convert to a finite number (`1e400` fails) | applicable nonblank cells (missingness is reported by completeness, not here) |
| % rule pass | passing evaluations of hard + inferred-convention rules | eligible evaluations (applicable and assessable) |
| % referential match | matched nonblank keys summed over the table's outgoing relationships | nonblank keys summed over those relationships; N/A for tables with no outgoing relationship |

**Key uniqueness disclosure.** The metric uses primary keys only. Probable duplicates with distinct IDs (the 25 client pairs in the raw data) do not lower it; they are covered by the decision log.

## Rules (`validation_rule_results.csv`)

Rule counts per stage: {'hard': 44, 'inferred_convention': 23, 'plausibility': 8}.

- **hard**: natural bounds (age >= 0, cash_pct in [0, 1], return_ytd >= -1, price > 0, ...), calendar definitions, standard code lists (US state codes, weekday names, 0/1 flags), date coverage, patterns, business-key uniqueness.
- **inferred_convention**: rules worked out from the data, not documented by Wildcat: code lists built from observed values (risk_profile, client_tier, account types, fee_type, txn_type, asset_class, region), sign rules (shares > 0, transaction amount > 0, fee amount > 0; direction comes from txn_type), conditional blanks, monthly rows on the 1st, and within-table reconciliations (amount = shares x price, fee formula, alpha identity).
- **plausibility**: assumed bands (return/alpha in [-0.6, 1.0], age 18-110, ...). Reported as warnings; never part of % rule pass.
- Each rule reports `not_applicable` (rule does not apply), `unassessable` (applies but the input is blank, invalid or nonfinite), and `eligible = passed + failed`. Unassessable evaluations are never counted as passes. Example: raw `9.28%` cannot be compared with -1, so it is unassessable.
- Invalid numbers (`inf`, `nan`, text) are rejected before any comparison; NaN never passes.

## Cross-table reconciliations (`validation_reconciliations.csv`)

Rows with blank or invalid join keys are excluded before any join and counted in `excluded_left` / `excluded_right`, so blank keys never match each other. Join cardinality is then checked; duplicate join keys stop that reconciliation (status `not evaluated`). Unmatched rows are reported separately from failures. A compared value that is blank or invalid on either side makes the pair `unassessable` (two blanks are never agreement). `pass_pct = passed / (passed + failed)`.

- R1: fee `aum_basis` = snapshot `aum` for the same client and month (one-to-one, exact decimal, +/- $0.01).
- R2a-c: advisor on each fee, snapshot and transaction = the client's advisor in dim_client (many-to-one).
- R3: snapshot `account_type` = client `primary_account_type` (many-to-one).
- R4: Advisory Fee transactions vs billed fees by client-month. A client-month containing any invalid amount is unassessable as a whole (partial totals are never compared). **Known unresolved discrepancy** (decision log Issue 13), reported for transparency and excluded from every score. Totals are shown side by side and never combined.

Within-table checks (shares x price, fee formula, alpha identity) are in the rule results, not here.

## IQR outliers (`validation_iqr_thresholds.csv`, `validation_iqr_flags.csv`)

- Fences: Q1 - 1.5 x IQR and Q3 + 1.5 x IQR, with Q1/Q3 from pandas `quantile` (linear interpolation).
- Reference population: the **clean** stage, valid finite values only, computed per group. The same fences are applied to raw and clean so the comparison is like for like.
- `initial_aum` uses one pooled population of all clients. Pooled thresholds were chosen to describe the overall client distribution of opening balances, so the flags show which accounts are unusually large relative to the whole client base (in practice the largest accounts): unusual, not wrong. Within-tier fences would answer a different question (unusual for its tier) and were not used.
- Transaction `amount` is grouped by `txn_type`, because dividends, deposits, fees and trades are different events with different typical sizes.
- A lower fence below 0 means no low-side flags are possible for that group.
- **Flagged means unusual, not necessarily wrong.** Large accounts and large trades are real. Flags are written to the reports only; clean tables are not modified. These flags are separate from the fixed-band `return_outlier_flag` added in cleaning.

## Limitations

- Raw values are judged as stored. `%` returns and `45.0` IDs are not reinterpreted at the raw stage, so they lower type validity, rule assessability and referential match there.
- Remaining issues stay visible in the clean stage: blank risk profiles lower completeness, snapshot months without fees appear in R1 `unmatched_right`, and R4 stays unreconciled.
- Plausibility bands and grouping choices are assumptions; changing them changes warning counts, not hard-rule pass rates.
- Allowed-value lists marked inferred were built from observed values; a new legitimate code would fail them.
